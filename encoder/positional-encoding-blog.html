01

Why a Transformer is blind to order

"The fox jumps over the dog" and "The dog jumps over the fox" use the exact same words. To you they mean opposite things — to raw self-attention they can look identical.

A recurrent network reads left to right, so order is baked into when it sees each word. A Transformer reads the whole sequence in parallel; attention is a set operation, fundamentally orderless. Shuffle the tokens and the math returns the same answer. Something has to inject "this one came first, that one came fifth."

🗂️

A pile of name tags

Cards dumped in a pile: you see every card but lost the order. Positional encoding stamps a seat number on each before the toss, so order is recoverable.

🕰️

Clock hands

Hands at different speeds pin down a moment at a glance. Each sinusoid is a hand; read them together to get a unique, smooth "position".

🎛️

A turned dial

RoPE turns each token's little vector a bit more per position — two tokens the same distance apart always differ by the same turn.

Concretely: each token becomes a vector of size $d$ (the hidden dimension). Positional encoding builds a second vector of the same size that depends only on position, and adds it on. Same words, different seat numbers → different vectors → attention can finally tell the sentences apart.

03

Is "positional encoding" the same as "positional embedding"?

Short answer: people use them interchangeably — but there is a real distinction worth knowing.

Both produce one vector per position, both get added to the token vectors, and both serve the identical purpose. The difference is where the numbers come from.

Positional encoding — the vectors are computed by a fixed formula (e.g. sine/cosine). Nothing is learned: feed in a position, a deterministic rule hands back its vector. The original Transformer used this.
Positional embedding — the vectors are learned parameters, a trainable lookup table exactly like the word-embedding table, one row per position. The model discovers good values during training. BERT and GPT-2 do this.

So: same role, different origin. "Encoding" leans toward fixed / hand-designed; "embedding" leans toward learned / data-driven. In casual writing the words blur because operationally they're both "a position-dependent vector you add to the input." When precision matters, reserve encoding for the formula kind and embedding for the learned kind.

RoPE muddies the line further: it's an encoding (fixed rotations, nothing learned) that acts on the vector multiplicatively rather than being added — so it isn't quite either of the two boxes above.
04

Sinusoidal encodings — the fixed formula

The original Transformer builds each position's vector from sines and cosines of many frequencies.

Even dimensions get a sine, odd dimensions get a cosine, and the wavelength stretches as you move along the vector. Read it as a stack of clocks: dimension pair $i=0$ ticks fast, higher $i$ ticks slowly. A position is the unique combination of where all the clocks point — like a smooth binary counter.

$$ PE(p,\,2i)=\sin\!\Big(\tfrac{p}{10000^{\,2i/d}}\Big)\qquad PE(p,\,2i+1)=\cos\!\Big(\tfrac{p}{10000^{\,2i/d}}\Big) $$

def sinusoidal(seq_len, dim, N=10000):
    i   = torch.arange(0, dim//2)
    div = torch.exp(-np.log(N) * (2*i / dim))   # 1 / N^(2i/d)
    pos = torch.arange(seq_len).unsqueeze(1)
    pe  = torch.zeros(seq_len, dim)
    pe[:, 0::2] = torch.sin(pos * div)        # even dims
    pe[:, 1::2] = torch.cos(pos * div)        # odd dims
    return pe
Why it's clever: deterministic (no params) and it extrapolates — the formula works for positions longer than any seen in training. Trig identities let the model recover relative offsets from dot products. Limit: hand-designed, so it can't adapt to the data, and very long contexts stretch its usefulness.
05

Learned positional embeddings

Skip the formula — just keep a trainable table, one row per position.

Row 0 is "position 0's vector," row 1 is "position 1's vector," and so on. The model learns whatever values minimise the loss, exactly like word embeddings but indexed by position instead of by token. Used in BERT and GPT-2.

Intuition — assigned seats the staff fine-tune. Rather than a mathematical seating rule, the venue keeps adjusting each seat's "personality" every show until the room works best. Flexible and tuned to the real crowd — but there are only as many seats as were ever installed. A guest in a seat that was never built has no vector.
class LearnedPositional(nn.Module):
    def __init__(self, max_len, dim):
        self.pos = nn.Embedding(max_len, dim)   # one row per position
    def forward(self, x):
        idx = torch.arange(x.size(1), device=x.device)
        return x + self.pos(idx)                  # add the learned vector
Trade-off: adapts to the data and is dead simple — but it cannot extrapolate past max_len (those rows never existed), can overfit, and adds parameters to the model.
06

Rotary encodings — RoPE

Most modern LLMs use RoPE. The twist: instead of adding a position vector, it rotates each token's vector by an angle proportional to its position.

Pairs of dimensions are treated as 2D points and spun by $m\theta_i$ at position $m$. Two tokens a fixed distance apart always differ by the same rotation, so the model reads relative distance directly — and the vector's length never changes (because $\cos^2+\sin^2=1$), which keeps training stable.

$$ \mathbf{\hat{x}}_m=\mathbf{R}_m\mathbf{x}_m=\begin{bmatrix}\cos(m\theta_i) & -\sin(m\theta_i)\\[2pt] \sin(m\theta_i) & \cos(m\theta_i)\end{bmatrix}\mathbf{x}_m,\qquad \theta_i=10000^{-2i/d} $$

def rotate_half(x):
    x1, x2 = x.chunk(2, dim=-1)
    return torch.cat((-x2, x1), dim=-1)
def apply_rope(x, cos, sin):
    return (x * cos) + (rotate_half(x) * sin)
Why LLMs adopted it: encodes relative position naturally ($\mathbf{R}_{m-n}=\mathbf{R}_m\mathbf{R}_n^\top$), extrapolates to longer contexts via the smooth geometric progression of angles, and preserves vector norms for stable training.
07

Relative encodings & ALiBi

The methods so far encode absolute seat numbers. But often what matters is the gap between two tokens.

Relative encodings drop a learned vector keyed on the signed distance $j-i$ between tokens, looked up from a table indexed by that distance. When you reference a neighbour you say "the person next to me," not their absolute seat — relative encoding gives attention that same handle, which transfers cleanly across any sequence length.

def forward(self, length):
    ctx = torch.arange(length)[:, None]      # i
    mem = torch.arange(length)[None, :]      # j
    rel = mem - ctx                            # distances (length, length)
    bucket = rel + self.max_relative_position  # shift to non-negative
    return self.relative_bias[bucket]          # a vector per gap

ALiBi (Attention with Linear Biases) is the lean cousin: it skips the lookup table and just subtracts a penalty proportional to distance straight from the attention scores before softmax — farther tokens get gently down-weighted. The per-head slope is $m_h = 1/2^{8h/H}$. Cheap, and famously good at letting models trained short run long.

Relative encodings power T5 and MPT; ALiBi powers Falcon. The common thread: bake distance into attention so the model generalises across lengths instead of memorising absolute slots.
